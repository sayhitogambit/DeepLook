# Your deployment, your credentials

[README](../README.md) · [Getting started](getting-started.md) · [DeepLook-API](https://github.com/sayhitogambit/DeepLook-API)

The local DeepLook CLI and local MCP tool need no account, email address, or API key. This repository provides software, not a preconfigured hosted account. Remote reads use the API URL and browser key from a server you operate or are authorized to access. No maintainer credentials are supplied.

## Separate the browser key from server administration

| Setting or credential | Where it belongs | Purpose |
| --- | --- | --- |
| Client `DEEPLOOK_API_URL` | CLI or MCP host's private process environment | Base URL of your API deployment |
| Client `DEEPLOOK_API_TOKEN` | CLI or MCP host's private process environment | Browser key used for `POST /v1/open` |
| Server `DEEPLOOK_ADMIN_TOKEN` | API server and trusted administrator tooling only | Manage accounts, browser keys, usage, logs, and sessions |
| Server `DEEPLOOK_API_TOKEN` | API server; optional static compatibility mode | A separate shared browser secret for `POST /v1/open` |
| Server `DEEPLOOK_DATA_DIR` | API server; private persistent storage | Account settings, hashed browser keys, counters, and bounded request metadata |

A named browser key is generated by the API and returned once when created or rotated. Named keys are associated with an account and subject to its request and concurrency limits. The optional static server token also authorizes page reads, but does not provide the account attribution and account limits of named keys. Neither browser credential authorizes administrator routes. An administrator token does not substitute for a browser key.

## Generate your own server secrets

Build the [API source](https://github.com/sayhitogambit/DeepLook-API) and the browser source, then configure the server according to its deployment guide. Generate independent secrets for independent roles. For example, in Bash, generate an administrator secret directly into the process environment:

```bash
export DEEPLOOK_ADMIN_TOKEN="$(node --input-type=module -e 'import { randomBytes } from "node:crypto"; process.stdout.write(randomBytes(32).toString("hex"));')"
```

This creates 32 random bytes, represented as 64 hexadecimal characters, without printing the value. Save the generated value in your own secret manager before closing the session; a new generation creates a different value. Do not paste it into a repository or reuse an example password.

The API also needs an absolute path to the built browser CLI and a private data directory outside the source checkout. For example, after creating a private persistent data directory:

```bash
export DEEPLOOK_CLI_PATH=/absolute/path/to/DeepLook/dist/cli.js
export DEEPLOOK_DATA_DIR=/absolute/path/to/private/deeplook-data
npm run api
```

Run that command from the built `DeepLook-API` checkout with the administrator secret already configured. The default bind is `127.0.0.1:47231`. Configure HTTPS at your deployment boundary before remote use, and follow the API repository's sandbox, storage, and deployment instructions.

Use the authenticated administrator endpoints to ensure an account and issue a browser key:

1. `PUT /v1/admin/accounts/:externalId` creates or ensures an account you name.
2. `POST /v1/admin/accounts/:externalId/tokens` issues a named browser key and returns its plaintext secret once.
3. Store that browser secret in the client's private `DEEPLOOK_API_TOKEN` environment. Keep the administrator secret on the server or in trusted administration tooling.

The account identifier is your own stable identifier; no Nymetric account is required. See the [API account management contract](https://github.com/sayhitogambit/DeepLook-API#account-management-contract) for request bodies, limits, rotation, and revocation. Handle issuance responses as secrets, without logging them.

### Optional static browser key

For a simple deployment using the compatibility token, generate a **separate** server browser secret:

```bash
export DEEPLOOK_API_TOKEN="$(node --input-type=module -e 'import { randomBytes } from "node:crypto"; process.stdout.write(randomBytes(32).toString("hex"));')"
```

Configure that same value in the API server and its authorized clients through your secret manager. Generating a new value separately on each machine will not work: the server and client must agree. This token is valid for browser reads only. For per-account quota, attribution, and revocation, use named browser keys instead.

## Configure the client

Set `DEEPLOOK_API_URL` to your deployment base URL, such as `https://your-api.example`. This is a placeholder; replace it with your own address. A path prefix is supported. HTTPS is required outside loopback; credentials, query parameters, and fragments in the base URL are rejected.

Supply the browser key as `DEEPLOOK_API_TOKEN` through a private environment, secret manager, or the interactive prompt in [Getting started](getting-started.md#3-use-your-own-remote-api-optional). Do not embed a real key in a command flag, URL, source file, shared host configuration, or issue report.

The client sends a bearer credential to your configured server. API redirects are rejected rather than forwarding credentials to another location. A remote read failure is reported without starting local Chrome. A remote `doctor` response confirms API liveness only; opening a public page is required to check the browser path and access permissions.

## Rotation, storage, and email

For a named key, create or rotate the key through the API, update the client's private environment, and revoke the old key if it is still valid. Restart long-running MCP hosts or clients when needed to load changed environment variables. A lost one-time secret requires a new key or rotation.

For a static browser token or administrator token, generate a replacement and update the server and authorized clients or administration tooling. Treat the API data directory and backups as private runtime state, and keep them outside public source distributions. Copying someone else's runtime database is not part of installing DeepLook.

Core CLI reads, MCP reads, API key generation, and account management require no SMTP server or email signup. An email service is not part of this setup. [support@getdeeplook.dev](mailto:support@getdeeplook.dev) is a contact address, not an authentication provider or a place to send keys.
